## 1. システム構成概要

`tdb` は単一プロセス・単一バイナリで動作するCLIアプリケーションである。利用者は REPL 上でコマンドを入力し、デバッガプロセスが `ptrace(2)` を用いて子プロセス（デバッギー）を制御する。

```
                +-----------------------------+
                |     利用者 (ターミナル)       |
                +---------------+---------------+
                                | コマンド文字列
                                v
                +-----------------------------+
                |      REPL (ui.c: repl)       |
                +---------------+---------------+
                                v
                +-----------------------------+
                | コマンド解析 (cmd.c もしくは   |
                | cmd_bison.c/cmd_parser/cmd_lexer)|
                +---------------+---------------+
                                v
                +-----------------------------+
                |   コマンドディスパッチ (ui.c: handle) |
                +---+------+------+------+------+---+
                    |      |      |      |      |
                    v      v      v      v      v
                 exec.c  expr.c dwarf.c sym.c memory.c
                    |      |      |      |      |
                    v      v      v      v      v
                +-----------------------------+
                |     ptrace(2) / ELFファイル    |
                +---------------+---------------+
                                v
                +-----------------------------+
                |   デバッギープロセス (子プロセス) |
                +-----------------------------+
```

heap.c はコマンドディスパッチ経由（`set`/`show`）に加え、`exec.c` の実行継続ループ（`continue_execution`）に直接フックされ、ブレークポイント処理と同じ INT3 機構を透過的に利用する。

## 3. ビルド構成

- `make` により `tdb`（デバッガ本体）、`target`、`leak_target`、`thread_target`、`fork_target`（サンプルデバッギー）を生成する。`thread_target`は`-pthread`付きでビルドする。
- コアソース: `dbg_globals.c util.c memory.c dwarf.c expr.c sym.c exec.c ui.c heap.c`（常時ビルド対象）。
- `bison`/`flex` の有無を `command -v` で検出し、以下のいずれかに切り替える。

| 条件 | コマンド解析 | 式評価 |
|---|---|---|
| bison/flexが両方揃っている | `cmd_bison.c` + 生成物（`cmd_parser.c/.h`, `cmd_lexer.c`） | `expr_ast.c`/`expr_parse.c`/`expr_eval_ast.c` + 生成物（`expr_parser.c/.h`, `expr_lexer.c`）、`-DHAVE_EXPR_BISON` |
| いずれか/両方が無い | `cmd.c`（手書き） | `expr.c` 内蔵の再帰下降パーサ |

- `.y`/`.l` から `.c` を生成するMakefileルールは、明示的に `bison`/`flex` を実行したとき（例: `clean` 後の再ビルド）にのみ発火する。生成済み成果物はリポジトリに含めて良い。
- `target`/`leak_target`/`thread_target`/`fork_target` はデバッガ本体のオブジェクトとリンクしない、独立した単体プログラムとしてビルドする。

## 6. 処理方式概要

### 6.1 プロセス起動・制御方式
- `fork()` 後、子プロセス側で `PTRACE_TRACEME` を発行し `execl()` する。親側は `PTRACE_EVENT_EXEC` 相当の停止を `waitpid` で待つ。
- 起動後、シンボルテーブル・行番号テーブル・変数情報をロードし、PIEであれば `/proc/<pid>/maps` からロードベースを求め、以降 `to_debug_addr`/`to_runtime_addr` によりELF静的アドレスと実行時アドレスを相互変換する。

### 6.1.1 SIGINT 転送方式
- デバッガ起動時（`main`）に `signal(SIGINT, sigint_handler)` を登録し、`SIGINT`（Ctrl+C）のハンドラを設置する。
- `sigint_handler` は `dbg.running` の場合にのみ、`threads[]` 中の各プロセスのルートスレッド（`tid == pid`のエントリ）ごとに `kill(pid, SIGINT)` を発行し、追跡中の全プロセス（`fork`で生成された子プロセスを含む）へ SIGINT を転送する。デバッギーが実行中でない場合（プロンプト待機中）は転送しない。
- `continue_execution` 内の `waitpid` 呼び出しはシグナルハンドラによる `EINTR` 割り込みを考慮し、`do { ret = waitpid(...); } while (ret == -1 && errno == EINTR);` のリトライループで包む。これにより、SIGINT ハンドラが `waitpid` を中断しても待機を継続し、デバッギーが SIGINT で停止した際の ptrace イベントを確実に捕捉する。
- デバッギーが SIGINT を受けて停止した場合、`continue_execution` は `WIFSTOPPED` 判定で `SIGINT` の停止として検知し、停止位置を表示してプロンプトに戻る（既存のシグナル停止処理と共通）。
- `help` 表示には `Ctrl+C  interrupt running program` の説明を含める。

### 6.2 ブレークポイント方式
- 対象アドレスの1バイトを読み取り退避（`original_data`）した上で `0xCC`（INT3）を書き込む。
- ヒット時、`rip`を1減算して本来の停止アドレスへ補正（`rewind_rip`）し、該当命令を一時的に元に戻して1命令だけステップ実行後、再度INT3を書き戻す（`step_over_breakpoint`）ことで実行継続を可能にする。
- `finish`（`up`）/`next` は、戻り先アドレスに同じ機構で一時ブレークポイントを設置し、ヒット時に自動解除する。

### 6.2a ウォッチポイント方式
- INT3方式のブレークポイントとは異なり、x86のハードウェアデバッグレジスタ（`DR0`-`DR3`：監視アドレス、`DR7`：制御、`DR6`：ステータス）を`PTRACE_PEEKUSER`/`PTRACE_POKEUSER`で操作する。CPUが持つスロット数の制約により最大4個までしか同時設置できない。
- `watch`コマンドは式を評価してアドレス・型を解決し、型サイズ（1/2/4/8バイトのいずれか、`/1`〜`/8`で明示指定も可）を`DR7`のLENフィールドへ、監視モード（書込のみ or 読み書き両方）をR/Wフィールドへ設定する。x86には読み取り専用の監視モードが存在しないため、`/r`指定時もR/W=11（読み書き両方）を用いる。
- `continue_execution`のトラップ処理内で`DR6`を読み取り、ビット0-3（各スロットのヒットフラグ）を確認する。`DR6`のビット4-13はハードウェア仕様上常に1が立つ予約ビットであるため、判定時はビット0-3のみをマスクして参照する。
- 書込監視は値が実際に変化した場合のみ停止・報告し、値が変わらない書込（スプリアスヒット）は無視して自動継続する。読み書き監視（`/r`）は読み取り時に値が変化しないため、ヒットの都度、値の変化有無によらず報告する。

### 6.2b マルチスレッド方式
- `run`時、`wait_for_exec`が`PTRACE_SETOPTIONS`で`PTRACE_O_TRACEEXEC`と同時に`PTRACE_O_TRACECLONE`を設定する。以後、デバッギーが`pthread_create`等で新規スレッドを生成すると、生成元スレッドに`PTRACE_EVENT_CLONE`付きの`SIGTRAP`が通知される。`PTRACE_GETEVENTMSG`で新規スレッドのtidを取得し`threads[]`へ登録する。
- `dbg.pid`はスレッドグループID（メインスレッド）を保持し、プロセス全体を対象とする操作（`kill`、`/proc/<pid>/maps`等）に用いる。`dbg.current_tid`は`regs`/`si`/`s`/`n`/`up`/`tb`/`p`/`set`等のコマンドが実際に対象とする「選択中スレッド」を保持し、`thread <num>`コマンドおよびブレークポイント/ウォッチポイント命中時の自動切替により更新される。
- **オールストップ方式**: いずれか1つのスレッドがブレークポイント・ウォッチポイント・シグナルにより停止すると、`sync_stop_other_threads`が他の実行中スレッド全てに`tgkill`で`SIGSTOP`を送り、その停止を`waitpid(-1, ..., __WALL)`で確認してから利用者にプロンプトを返す。`tgkill`の第1引数（対象のtgid）には各スレッド自身の`threads[i].pid`を用いる（`fork`で複数プロセスを追跡している場合、`dbg.pid`固定では他プロセスのスレッドに対して失敗するため）。`c`は追跡中の全スレッド（全プロセス分）を`PTRACE_CONT`で再開する。
- ブレークポイント（INT3）はプロセスの共有アドレス空間に設置されるためスレッドを問わず検知できるが、ウォッチポイント（デバッグレジスタ）はスレッド単位の状態のため、`watch`設置時に存在する全スレッドへ`arm_watch_slot`を適用し、以後生成される新規スレッドにも自動的に伝播する。
- 複数スレッドがほぼ同時にブレークポイントへ到達する競合状態に対応するため、`sync_stop_other_threads`が他スレッドの停止を待つ際、対象スレッドが（同期用に送った`SIGSTOP`ではなく）自らブレークポイントに命中していた場合は、通常のヒット処理と同じ手順（元データ復元・1命令実行・INT3再設置）を経由させる。この際、既に送信済みの`SIGSTOP`がシングルステップの実行そのものを一瞬横取り（preempt）し命令が実際には進まないまま完了したように見えるケースがあるため、レジスタ（`rip`）が実際に進んだことを確認できるまでシングルステップをリトライする。

### 6.2c スケジューラロック方式（`lock`/`unlock`）
- `lock <tid>`は、指定tidが`threads[]`に存在することを確認した上で、ファイルスコープの静的変数`locked_tid`にそのtidを設定し、`dbg.current_tid`も同tidへ切り替える。
- `continue_execution`冒頭の再開ループは、`locked_tid`が0以外の間、`threads[]`のうち`locked_tid`と一致するものだけへ`PTRACE_CONT`を発行し、それ以外は（選択中スレッドであっても）`running=0`のまま再開せずスキップする。したがって`c`を実行してもロック対象以外のスレッドは一切進行しない。
- `si`/`s`/`n`/`up`はいずれも冒頭で「`locked_tid != 0`かつ`dbg.current_tid != locked_tid`」を確認し、該当する場合はエラーメッセージ（「current thread (tid=N) is not the locked thread」）を表示して何も実行せずに戻る。これにより、`thread <num>`でロック対象以外のスレッドへ選択を切り替えた状態で`si`等を発行しても、そのスレッドが実行されてしまうことはない。この確認が無いと、`next`/`up`が内部的に呼ぶ`continue_execution`がロック対象以外のtidを待ち続けて永久にブロックする経路も生じる。
- ロック中にロック対象スレッドが新規スレッドを生成した場合、生成された新規スレッドは通常どおり`threads[]`へ登録されるが、SIGSTOPハンドラは`locked_tid`が設定されている間、新規スレッドのtidが`locked_tid`と一致しない限り`PTRACE_CONT`で再開しない（登録だけして停止状態を保つ）。ロック対象以外が増殖してロックの意味が失われることを防ぐ。
- `unlock`は`locked_tid`を0に戻すのみで、その場では他スレッドを再開しない。次に発行される`c`の再開ループが`locked_tid == 0`として全スレッドを`PTRACE_CONT`する。
- ロック対象スレッドが解除前に終了した場合（`remove_thread`が該当tidの終了を検知した際）、`locked_tid`を自動的に0へ戻すと同時に、その場で`threads[]`中の`running == 0`な全スレッドへ`PTRACE_CONT`を発行して再開する。ロック中に再開を保留されていた他スレッドは、次の`c`が発行されるまで待たされることなく即座に動き出す（この即時再開を行わない場合、`continue_execution`の待機ループが誰からも新たなイベントが来ないまま永久にブロックする）。
- `threads`コマンドの一覧表示では、`locked_tid`と一致する行に`L`マーカーを付し、ロック中は末尾に凡例行を追加する（5章参照）。

### 6.2d マルチプロセス方式（`fork`/`vfork`）
- `wait_for_exec`が`PTRACE_SETOPTIONS`で`PTRACE_O_TRACECLONE`と同時に`PTRACE_O_TRACEFORK`/`PTRACE_O_TRACEVFORK`も設定する。これらのオプションは`ptrace(2)`の仕様により以後生成される子孫（さらなる`fork`/`clone`）へ自動的に継承されるため、子プロセスが自分自身のスレッドを生成した場合も個別に再設定する必要はない。
- デバッギーが`fork`/`vfork`すると、呼び出し元スレッドに`PTRACE_EVENT_FORK`/`PTRACE_EVENT_VFORK`付きの`SIGTRAP`が通知される（`PTRACE_EVENT_CLONE`と同様、`(status >> 16) & 0xffff`で判別）。`PTRACE_GETEVENTMSG`で新規プロセスのpidを取得し、`threads[]`へ`tid == pid`（そのプロセス自身がルート）として登録する。この判定・登録処理は、スレッド生成時のCLONE処理と共通の内部関数`handle_new_thread_event`で行い、`continue_execution`本体と`sync_stop_other_threads`の両方の待機ループから呼ばれる（後者は、同期のためにSIGSTOPを送っている最中の別スレッドが、ちょうどそのタイミングで新規スレッド/プロセスを生成するケースに対応するため）。
- 新規プロセスの検知直後は`PTRACE_CONT`で通知元スレッドのみ再開し、新規プロセス自身はまだ再開しない。新規プロセスの初回停止（`SIGSTOP`として配送される）を確認してから再開する処理は、スレッド生成時と同一のSIGSTOPハンドラに一元化されている（順序が不定な2つの通知〈FORK/VFORKイベント通知と新規プロセス自身の初回停止〉を安全に扱うため）。
- ブレークポイント（INT3）は各プロセスが個別のアドレス空間を持つため、`fork`時点で既に設置済みのバイト列はコピーオンライトにより子プロセスへ自動的に引き継がれるが、`fork`後に`set_breakpoint`/`delete_breakpoint`が実行された場合は、追跡中の全プロセス（`threads[]`中の`tid == pid`の各エントリ）へ明示的に設置・復元を行う。
- ウォッチポイント（デバッグレジスタ）はスレッド単位のCPU状態であり`fork`では引き継がれないため、新規プロセスのルートスレッドに対しても既存の全ウォッチポイントを`propagate_watchpoints_to_thread`で適用する（スレッド生成時と同じSIGSTOPハンドラ内の処理を流用）。
- プロセス終了の扱いは「`dbg.pid`（元プロセス）が終了したら全体終了」ではなく「`threads[]`が空になった（追跡中の全プロセスの全スレッドが終了した）時点で全体終了」に一般化されている。子プロセスが1つ終了しても他のプロセスが残っていればセッションは継続し、「process pid=N exited (other tracked processes remain)」を表示するのみで停止しない。
- `kill`は`threads[]`中の全プロセス（`tid == pid`の各エントリ）へ個別に`SIGKILL`を送り、全スレッド分の終了イベントを`waitpid`で回収してからクリアする。
- デバッギーが自分自身の子プロセスを`waitpid`で回収するようなプログラム（`fork_target.c`のような、fork後に親が子を待つ典型パターン）は、その回収に伴って自分自身が受け取る`SIGCHLD`もptraceにより横取り・報告対象となる。これを利用者に見せる停止として扱うと、子プロセスが終了する度に`c`を要求してしまい実用に耐えないため、`SIGCHLD`はgdbの既定動作と同様、`PTRACE_CONT(tid, 0, SIGCHLD)`で自動的にデバッギーへ転送し、停止せずに継続する。
- `print`/`set`等が経由するメモリアクセス（`read_memory`/`poke_word`/`peek_word`、memory.c）は`dbg.current_tid`が属するプロセスに対して行われる（かつては`dbg.pid`固定だったため、子プロセス停止中に`print`すると誤って元プロセスのメモリを参照してしまう不具合があった）。
- 本方式は、子プロセスが`fork`後に`execve`で別プログラムへ切り替わらないことを前提とする（要件定義書7章参照）。そのため、ELFシンボル・DWARF情報・PIEロードベース（`dbg.is_pie`/`dbg.load_base`）はプロセス間で共有する1セットのままでよく、プロセスごとに個別に保持する設計にはなっていない。

### 6.3 シンボル解決方式
- ELFファイルを `mmap` し、ELFヘッダのマジック確認・`ET_DYN`判定によるPIE検知を行う。
- `.symtab`/`.strtab` から `STT_FUNC`/`STT_OBJECT` のシンボルを抽出し `symbols[]` に格納する。
- 動的リンクバイナリについては `.dynsym` と `.rela.plt` からPLTスタブのアドレスも解決する。

### 6.4 DWARF解析方式
- `.debug_abbrev` の略語テーブルを読み込んだ上で `.debug_info` のDIEツリーを走査し、コンパイル単位・関数・変数・型のDIEを解釈する。
- 型DIEは `type_info_t` に変換して `type_cache[]` にキャッシュし、再解析コストを抑える。
- `.debug_line` は行番号プログラムのステートマシンとして解釈し、アドレス→file:lineの対応表（`line_entries[]`）を構築する。

### 6.5 式評価方式
- ビルド構成に応じて2系統のいずれかが有効になる。
  - 自前実装（`expr.c` 内の再帰下降パーサ）: 数値・識別子・`$reg`・`.`/`->`/`[]`・単項/二項演算子を直接評価。
  - bison/flex実装（`expr_parser.y`/`expr_lexer.l` + `expr_ast.c`/`expr_eval_ast.c`）: 一旦AST（`expr_ast_t`）を構築し、`eval_expression_bison`等で評価。
- どちらの経路でも、識別子はまずDWARF変数（スコープ内のローカル/引数、グローバル）として解決を試み、次にレジスタ名として解決する。

### 6.6 ヒープトレース方式
- `malloc`/`free`/`calloc`/`realloc` のアドレスをシンボル解決（実シンボル優先、無ければPLTシンボル）し、各エントリポイントにブレークポイントと同じINT3機構でフックを設置する（最大4フック）。
- `continue_execution` のトラップ処理順序は「ヒープフック（finish待ち→エントリトラップ）→ next/finish一時ブレークポイント→ユーザーブレークポイント」の順とし、ヒープフックのトラップは利用者に見せず自動的に実行を継続する。
- 確保系フックはエントリ時に引数（サイズ等）と呼び出し元アドレスを記録し、戻り先に一時ブレークポイントを設置して `rax`（戻り値ポインタ)を捕捉した時点で確保記録を確定する。解放系フックはエントリ時点で対応記録を解放済みにする。
- 確保記録は固定長配列 `heap_allocs[MAX_HEAP_ALLOCS]` で管理し、`show heap`/`show leaks` は生存中の記録を一覧表示、プロセス終了時に自動でリーク件数サマリ（`N leak(s) at process exit` または `no leaks detected`）を表示する。

## 7. 制限値一覧

| 定数 | 値 | 内容 |
|---|---|---|
| MAX_BREAKPOINTS | 32 | ユーザーブレークポイント上限 |
| MAX_SYMBOLS | 1024 | ELFシンボル格納上限 |
| MAX_LINE_ENTRIES | 4096 | DWARF行テーブルエントリ上限 |
| MAX_VARS | 256 | DWARF変数エントリ上限 |
| MAX_TYPE_CACHE | 128 | 型情報キャッシュ上限 |
| MAX_ABBREVS | 64 | コンパイル単位ごとの略語テーブル上限 |
| members[16] | 16 | 構造体1型あたりの最大メンバ数 |
| MAX_HEAP_HOOKS | 4 | ヒープフック対象関数数（malloc/free/calloc/realloc） |
| MAX_HEAP_ALLOCS | 4096 | 追跡可能な確保記録数 |

いずれも固定長配列であり、上限到達時は動的拡張せず、エラー表示または黙示的な打ち切り（それ以上格納しない）とする。

## 8. エラー処理方針

- システムコール／`ptrace`失敗: 戻り値`-1`判定 + `perror()`によるエラー内容表示。当該処理を中断し呼び出し元へ`-1`または`void`で復帰する。
- 利用者操作起因の想定内エラー（未起動状態でのコマンド実行、不正アドレス、未知シンボル、書式誤り等）: `printf`による短いメッセージ表示のみとし、REPLは継続する。
- コマンド／式パーサのエラー: 固定長バッファ（`errbuf`/`cmd_parse_error`/`expr_parse_error`）にメッセージを格納し、呼び出し元が表示する。
- 上限超過（配列容量不足）: 書き込み前に容量チェックを行い、超過時はメッセージ表示のうえで格納をスキップする（クラッシュさせない）。
- デバッガプロセス自体が明示的に終了するのは `q` コマンド実行時（`exit(0)`）のみとし、それ以外の異常はREPLループ内で局所的に処理する。
