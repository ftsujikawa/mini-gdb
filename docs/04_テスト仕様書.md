## 1. テスト方針

- 要件定義書 5章の各機能要件（FR-xx）に対応するテストケースを網羅する。
- 実行手段は `tdb` REPL上での対話操作とし、サンプルデバッギー `target.c`（ビルド後 `target`）および `leak_target.c`（ビルド後 `leak_target`）を主な検証対象プログラムとして用いる。
- 正常系（想定通りの操作）に加え、異常系（未起動時の操作、上限超過、不正引数等）についても検証する。
- 出力内容は実装のログ整形に依存する部分があるため、期待結果は「意味的に正しいこと」（値・アドレス・行番号・件数等が正しいこと）を基準とし、文言の完全一致までは求めない。
- ビルド構成（bison/flexあり/なし）双方で機能要件が満たされることを確認する（13章）。

## 4. プロセス起動・実行制御テスト

前提: `target`をビルド済み。`(tdb)`プロンプトが表示されている状態から開始。

| No | 項目 | 手順 | 期待結果 |
|---|---|---|---|
| T-01 | 通常起動 | `run target` | デバッギーが起動し、`main`直前で停止（またはロード完了メッセージ）。以後`c`等が受け付けられる |
| T-02 | PIEロードベース取得 | `-fPIE`でビルドした対象で`run <pie_program>`後`b add`→`c`→`regs` | ブレークポイントが実アドレス（ロードベース加算後）で命中し、`regs`表示のPCが妥当な範囲であること |
| T-03 | continue | T-01の後、`b add`でブレークポイント設置し`c` | `add`関数の先頭（プロローグ通過後）で停止し、停止行が表示される |
| T-04 | 命令ステップ | `run target`直後`si`を数回実行 | 実行するたびに1命令ずつ進み、`regs`のrip値が変化する |
| T-05 | ソース行ステップ(s) | `add`関数呼び出し行で`s` | `add`関数の内部（1行目）に入って停止する |
| T-06 | ステップオーバー(n) | `main`内の`add`呼び出し行で`n` | `add`関数内部に入らず、`main`の次の行で停止する |
| T-06a | ステップオーバー時の分岐スキップ | `leak_target`を`b main`→`c`後、`if (!ok \|\| !leak_a \|\| !leak_b) {`の行（条件が偽になる行）で`n` | `if`本体（条件が真の場合のみ実行される行）を経由せず、条件が偽の場合に実際に実行される次の行で停止する（プロセスが終了してしまわないこと） |
| T-06b | ステップオーバー中のブレークポイント命中 | `target`を`b main`→`c`後、`add`呼び出し行に到達するまで`n`を繰り返し、`b add`で`add`内部にブレークポイントを設置してから`n` | `add`の呼び出し元行を素通りせず、`add`内部のブレークポイントで「breakpoint hit」として停止する |
| T-07 | 関数リターンまで実行(up) | `add`関数内部から`up` | `add`関数のリターン後、呼び出し元（`main`のadd呼び出し直後）で停止する |
| T-08 | プロセス正常終了 | 終了するプログラムに対し`c`を繰り返す（またはループ無しプログラム使用） | プロセス終了が通知され、以後`run`以外のプロセス依存コマンドはエラーになる |
| T-08a | 強制終了(kill) | 無限ループプログラムを`run`→ブレークポイント停止中（または`c`実行後の停止中）に`kill` | 「process killed」等のメッセージが表示され、デバッギーが終了する（OS上にプロセス・ゾンビが残らない）。`tdb`自体は終了せず`(tdb)`プロンプトに戻る |
| T-08b | 強制終了後の状態 | T-08aの後、`regs`等のプロセス依存コマンドを実行 | 「no process」が表示される |
| T-08c | 未起動時のkill | デバッギー未起動の状態で`kill` | 「no process」が表示され、REPLは継続する |
| T-08d | kill後の再起動 | T-08aの後、`run target` | 新たなプロセスが起動し、以後`c`・`b`等が通常通り操作できる |
| T-09 | SIGINT転送（Ctrl+C） | 無限ループプログラムを`run`→`c`で実行継続状態にした後、Ctrl+Cを入力する | デバッガが SIGINT をデバッギーに転送し、デバッギーが停止する。停止位置（ソース行またはアドレス）が表示され、`(tdb)` プロンプトに戻ること。以後`p`・`b`等のコマンドが操作可能であること |

## 5a. ウォッチポイントテスト

前提: `target`を`b main`→`c`でヒットさせた状態（ローカル変数`x`,`y`,`ts`,`ts_ptr`,`sa`,`sa_ptr`,`pm`が有効）。

| No | 項目 | 手順 | 期待結果 |
|---|---|---|---|
| T-19c | 設置 | `watch x` | 「Hardware watchpoint N: x」が表示され、`show watch`に登録される |
| T-19d | 一覧表示 | 複数の`watch`実行後`show watch` | 設置した全ウォッチポイントが番号・有効フラグ・アドレス・サイズ・モード（w/rw）・対象式とともに表示される |
| T-19e | 値変化での停止 | `watch x`→`c` | `x`へ実際に書き込みが行われた時点で停止し、「Old value = ...」「New value = ...」が型に応じた形式で表示される |
| T-19f | サイズ自動判定エラー | `watch ts`（12バイトの構造体） | 「cannot watch value of size 12」等のエラーとなり設置されない |
| T-19g | サイズ明示指定 | `watch /4 ts` | T-19fで失敗した構造体変数も、先頭4バイトのみを対象に設置できる |
| T-19h | 読み書きアクセス監視 | `watch /r <expr>`→`c` | 値の変化有無によらず、読み取りアクセスの時点でも「Hardware access (read/write) watchpoint」として停止・報告される |

| T-19k | 削除 | `watch x`→`show watch`で番号確認→`del w<num>` | 「Watchpoint N deleted」等のメッセージが表示され、`show watch`から該当エントリが消える。残りのウォッチポイントは引き続き正しく機能する |

| T-19m | プロセス終了時のリセット | ウォッチポイント設置後`kill`（または通常終了）→`run target` | 新しいプロセスではウォッチポイントが引き継がれず、`show watch`は空、`watch`で新規に4個まで再設置できる |

## 8a. マルチスレッドテスト

前提: `thread_target`をビルド済み（`make thread_target`、`-pthread`が必要）。`thread_target.c`は3つのワーカースレッドが共通関数`worker`を呼び出し、共有変数`shared_total`へ書き込む構成。

| No | 項目 | 手順 | 期待結果 |
|---|---|---|---|
| T-69 | スレッド生成検知 | `run thread_target`→`b worker`→`c` | いずれかのワーカースレッドがブレークポイントにヒットし、停止表示の`[+] pid=N tid=M`でNとMが異なる値（プロセス全体のpidと実際にヒットしたスレッドのtid）として表示される |
| T-70 | スレッド一覧表示 | T-69の後 `threads` | 追跡中の全スレッド（メイン+生成済みワーカー）が番号・tid付きで一覧表示され、現在選択中のスレッドの行に`*`が付く。ブレークポイントで停止しているワーカーの行には`in worker+0x<off>`（関数名+オフセット）と`at thread_target.c:<line>`（ファイル:行）が付記される |
| T-71 | 複数スレッドでのブレークポイント命中 | T-69の後 `c` を繰り返す | 別のワーカースレッドが同じブレークポイントにヒットし、`threads`一覧のスレッド数が増えていく。全ワーカーがヒットしたら`del 1`等でブレークポイントを解除しないと停止しなくなる |
| T-72 | スレッド切替 | `thread <num>`（`threads`で確認した別スレッドの番号） | 「switched to thread N」等のメッセージと切替先スレッドの現在位置が表示され、以後の`regs`/`tb`が切替先スレッドを対象とする |
| T-73 | スレッド別レジスタ/バックトレース | T-72の後 `regs`・`tb` | 切替先スレッドの`rip`・レジスタ値・バックトレースが表示され、他スレッドの値と異なる |
| T-74 | ウォッチポイントの全スレッド伝播 | `del 1`（ブレークポイント削除）→ `watch shared_total` → `c` | いずれかのワーカースレッドが`shared_total`に書き込んだ時点で停止し、`Old value`/`New value`が表示される。どのワーカースレッドの書き込みでも検知できること |
| T-75 | 新規スレッドへの伝播 | ウォッチポイント設置**前**にはまだ生成されていないワーカースレッドが後から生成される場合 | 新たに生成されたスレッドの書き込みも同じウォッチポイントで検知される（設置後に生成されたスレッドにも自動適用されること） |
| T-76 | 正常終了 | T-74の後、全ワーカーの書き込みが終わるまで`c`を繰り返す | 3つのワーカー全ての「contributed」メッセージと「all done」が表示され、プロセスが正常終了する。強制終了・クラッシュ（signal=11相当）が発生しないこと |
| T-77 | 強制終了時のクリーンアップ | マルチスレッド実行中に`kill` | デバッギー（全スレッド）が終了し、OS上にゾンビ・残存スレッドが残らない。`threads`は空を返す |
| T-78 | 安定性（繰り返し実行） | T-69〜T-76の手順を10回以上連続実行 | 毎回同様に正常終了し、SIGSEGV等によるデバッギーのクラッシュ、`tdb`のハングが発生しないこと（スレッド生成・ブレークポイント同期のタイミング依存の競合状態が無いことの確認） |
| T-79 | 既存単一スレッド機能の非破壊確認 | `target`/`leak_target`（非マルチスレッド）で T-01〜T-77 のうち適用可能な既存テストを再実行 | マルチスレッド対応前と同一の結果が得られる（回帰がないこと） |
| T-80 | スケジューラロック設置 | T-69の後 `threads` で確認したワーカーのtidを指定して `lock <tid>` | 「locked to tid=N」等のメッセージと、ロック対象スレッドの現在位置が表示される |
| T-81 | ロック中の実行制限 | T-80の後 `c` | ロック対象スレッドのみが進行し「worker N contributed...」が表示される。`threads`で確認すると、ロック対象以外のスレッド（メインおよび未ヒットのワーカー）は`lock`実行前と全く同じ`rip`のまま停止している |

## 14. 合否判定基準

- 各テストケースにおいて「期待結果」欄の内容を満たした場合を合格とする。
- 異常系テスト（11章）は、エラーメッセージが表示されつつ`tdb`プロセスおよびREPLが継続動作することを合格の必須条件とする（クラッシュ・ハングを不合格とする）。
- 制限値テスト（12章）は、上限到達時にクラッシュしないことを最優先の合格基準とし、表示件数の切り捨て自体は仕様上の既知制約として許容する。
- 全テストケースを実施し、不合格項目がある場合は詳細設計書の該当モジュールを見直したうえで再テストを行う。
