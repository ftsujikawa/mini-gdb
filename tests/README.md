# tdb 自動テストスイート

`docs/04_テスト仕様書.md` の各章に対応する自動テストです。実際に
`tdb`をpty経由で対話的に操作し（`stdbuf`等の外部ツールもpexpect等の
サードパーティ依存も使わず、Python標準ライブラリの`pty`/`subprocess`
のみで駆動）、出力を検証します。

## 実行方法

```sh
make            # tdb本体・サンプルデバッギー(target/leak_target/
                # thread_target/fork_target)を先にビルドしておく
python3 tests/run.py             # 全章を実行
python3 tests/run.py 08a 08b     # 指定した章のみ実行（複数指定可）
```

引数に渡す章キーは `tests/run.py` の `SECTIONS` に列挙されている
`"04"`, `"05"`, `"05a"`, `"06"`, `"07"`, `"08"`, `"08a"`, `"08b"`,
`"09"`, `"10"`, `"11"`, `"12"` です。テスト仕様書の章番号と対応します。

終了コードは、1件でもFAIL/ERRORがあれば非0になります（CI等での判定に
使えます）。

## 構成

| ファイル | 対応する章 |
|---|---|
| `harness.py` | 全章共通のテスト駆動ライブラリ（後述） |

| `test_04_process.py` | 4章 プロセス起動・実行制御（T-01~T-09） |
| `test_05_breakpoint.py` | 5章 ブレークポイント（T-10~T-19b） |
| `test_05a_watchpoint.py` | 5a章 ウォッチポイント（T-19c~T-19m） |
| `test_06_expr.py` | 6章 変数・式評価（T-20~T-36） |
| `test_07_debuginfo.py` | 7章 デバッグ情報・ソース表示（T-40~T-50） |
| `test_08_state.py` | 8章 実行状態参照（T-60~T-68） |
| `test_08a_thread.py` | 8a章 マルチスレッド（T-69~T-83） |
| `test_08b_fork.py` | 8b章 マルチプロセス／fork（T-85~T-89c） |
| `test_09_heap.py` | 9章 ヒープトレース／リーク検出（T-70~T-77、本章独自の番号） |
| `test_10_repl.py` | 10章 REPL・コマンドライン（T-80~T-84） |
| `test_11_errors.py` | 11章 異常系（T-90~T-97） |

13章は`bison`/`flex`の有無で`make`の挙動そのものを切り替える章であり、
本スイートを両構成で実行すること自体がその確認に相当します。

## `fixtures/` の各プログラム

`dbg.h`/`heap.c`の固定上限を実際に超える規模のプログラムで、
`test_12_limits.py`実行時に`gcc`でビルドされます（メインの`Makefile`
には含めていません。これらは限界値確認専用の使い捨てフィクスチャで、
デバッガ本体のサンプルデバッギー一式とは役割が異なるためです）。

| ファイル | 検証する上限 |
|---|---|
| `big_struct.c` | 構造体メンバ数（`type_info_t.members[16]`、20個の構造体で超過させる） |
| `heap_stress.c` | ヒープ確保記録数（`MAX_HEAP_ALLOCS`=4096、4200回`malloc`する） |
| `many_symbols.c` | シンボル数（`MAX_SYMBOLS`=1024、関数1100個を定義する） |

## harness.pyの設計

`Session`クラスが1つの`tdb`プロセスをpty越しに保持し、`cmd(line)`で
コマンドを送って次のプロンプトが出るまでの出力を返します。pty経由に
しているのは、パイプ相手だと`tdb`の標準出力がフルバッファリングされ、
`stdbuf -oL`のような外部ツールなしには出力を即時に受け取れないためです
（実ターミナル相手なら通常のC標準ライブラリの動作で行バッファになる）。

`run_scenario(reporter, [(test_id, description, fn), ...])`は、
テスト仕様書自体が多くの箇所で「T-69の後...」のように手順を連鎖させて
記述していることに合わせて、1つの`Session`上で複数のテストIDを順番に
実行するヘルパーです。途中の手順が失敗すると、それに依存する以降の
手順は（状態が不明なため）実行せず、失敗はその場で報告されます。

`Session.close()`は`q`の前に必ず`kill`を送ります。`q`は`tdb`自身を
`exit(0)`するだけでデバッギーを終了させないため、`lock`やウォッチ
ポイント同期で本物のSIGSTOPにより一時停止させられていたスレッドが、
トレーサ終了によるデタッチ後もそのまま永久に停止した状態で取り残される
ことがあります。これを怠ると、テストスイートを何度も実行するうちに
前回セッションの停止したままの残存プロセスが蓄積し、システムを再現
困難な形で不安定化させます。

## 本スイート作成中に見つけて修正した実際の不具合

このテストスイートを実装・実行する過程で、以下3件の実際の不具合を
発見し、`exec.c`側を修正しました（テストコード側の問題ではなく、
`tdb`本体の不具合です）。

1. **`run`の二重実行がデバッギーをリークする**: 実行中に再度`run`する
   と、既存のデバッギーを`kill`せずに新しいものを起動していたため、
   古いプロセスが同じターミナルの標準出力を共有したまま永久に残存し、
   両プロセスの出力が混在する不具合があった。`run_target()`の冒頭で
   `dbg.running`なら`kill_process()`するよう修正。
2. **`watch`/`b`が、既に終了した(まだreapされていない)スレッド1つの
   せいで全体が失敗する**: `watch_command`・`set_breakpoint`が追跡中の
   全スレッド/全プロセスへ設定を適用するループ中、いずれか1つで
   `ESRCH`（対象が既に終了）が発生すると、他の生存中スレッド分も含めて
   即座に失敗し、ウォッチポイント/ブレークポイントが一切登録されない
   不具合があった。個々の失敗はスキップして継続するよう修正。
3. **（最重要）ごく低い確率でスレッドが永久にハングする**: あるtidの
   `running`フラグが既に1（実行中）と信じている状態で、そのtid宛ての
   `SIGSTOP`を受信すると、これを常に「何もしなくてよい」ものとして
   無視していた。しかし、以前の`sync_stop_other_threads`の同期ラウンド
   で送った`SIGSTOP`がCPU負荷等により配送が遅延し、そのラウンドが
   とっくに終わって当該スレッドが正常に再開・動作した*後*に届くことが
   あり得る。この場合、実際にそのtidはこのSIGSTOPによって今まさに
   本物のptrace-stop状態に陥っているにもかかわらず、コード側は
   「対応不要」と判断してしまい、誰からも二度と`PTRACE_CONT`されない
   まま永久に停止したスレッドが残ってしまう（`/proc/<pid>/task/<tid>/
   status`で`State: t (tracing stop)`として確認できる。他スレッドが
   `pthread_join`等でそれを待っていれば、プロセス全体が事実上デッド
   ロックする）。全CPUコアへの負荷生成と多数回の再試行を組み合わせて
   実際に再現・特定した（通常の負荷下では発生確率が極めて低く、単純な
   繰り返し実行だけでは再現しなかった）。`continue_execution`の
   `SIGSTOP`処理を、この「古い/取り残された`SIGSTOP`」ケースも
   `sync_stop_other_threads`自身が持つ「resume-and-reabsorb」と同じ
   方針で即座に再開するよう修正。

## 既知の制約

- マルチスレッド／マルチプロセス系の章（8a/8b）は実スレッド・実プロセス
  の実行タイミングに依存するため、固定回数の`c`ではなく「期待する出力
  が現れるまで`c`を繰り返す（上限付き）」方式で検証しています。それでも
  タイミング次第で通常より時間がかかることがあります。
- 13章・T-09（SIGINT）・T-78/T-89b（安定性の繰り返し実行）は環境依存性
  が比較的高い章/項目です。CI環境で不安定な場合は、まず該当章のみを
  `python3 tests/run.py <章>`で単独実行し、再現するか確認してください。
